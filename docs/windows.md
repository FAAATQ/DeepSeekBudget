# Windows 这一侧

macOS 与 Windows 在同一个 Tauri 应用里不是「同一份代码换个目标平台」。窗口该往哪边长、什么时候该关、圆角由谁画、tooltip 能放多少字 —— 这几件事**两边各不相同**，而且差异全都藏在默认值里，不跑一遍看不出来。

这份文档记录本项目在 Windows 上真正量到的东西。

> **一个反直觉的结论**：这个项目一度在 Windows 上**比在 macOS 上更容易验证** —— macOS 的 `screencapture` 被屏幕录制权限拒绝，而 Windows 的 `CopyFromScreen` **不需要任何权限**。所以「换个平台」在这里不只是功能差异，更是**可验证性的差异**。
>
> ⚠️ **但这条已经作废（2026-09-13）**：macOS 那边的权限通了，菜单栏、弹窗、圆角现在都能直接截图核对。见 [macos.md](macos.md) 第五节。

## 一、弹窗该往哪边长：按可用空间，不按平台

### 症状（实测）

```
rect=(2074,1446)-(2410,1925)
```

面板顶端在 1440 高的屏幕**底部之下 6px** —— 整个 app 唯一的界面，完全够不着。

### 根因

定位函数写死了「永远在图标下方」。这对 macOS 是对的：菜单栏在屏幕**顶部**，图标下方永远是内容区。到了 Windows，任务栏在**底部**，图标的**下边缘就是屏幕的下边缘**，再往下就是屏幕外。

同时还有两个次级错误：只钳制了 X 不钳制 Y；以及用的是**整块显示器**而不是**工作区**（工作区已经扣掉了任务栏）。

### 修法

```rust
// 下方放得下就放下方，否则放上方。两个分支在真实世界里都会走到：
// 前者是 macOS 菜单栏，后者是 Windows 任务栏。
let below = icon.bottom() + gap;
let above = (icon.y - gap).min(work.bottom()) - panel_h;
let max_y = (work.bottom() - panel_h).max(work.y);
```

**关键设计：按「哪边放得下」决定，而不是按 `cfg!(target_os)` 决定。** 这样一来，任务栏在左/右/上、或者将来 Windows 把任务栏挪到顶部，都不需要改代码。

`panel_origin` 是一个**纯函数** —— 不碰窗口、不查系统：

```rust
pub fn panel_origin(icon: PixelRect, work: PixelRect, panel: (i32, i32), gap: i32) -> (i32, i32)
```

**这正是它能在没有 Windows 的机器上被测试的原因**，也是「引擎不自己读系统状态、由外壳把事实传进去」这条设计在 UI 代码里的同一种应用。**六个测试**钉住了：底部任务栏 / 顶部菜单栏两种位置、面板不覆盖任务栏、水平方向被钳进工作区、第二显示器按**它自己**的工作区定位、以及面板比工作区还高时仍可够到。

修后实测：`rect=(2074,916)-(2410,1395)`，紧贴任务栏上方。

### 一个不显然的细节：向上时不该贴着图标

向上展开时，面板**贴工作区边缘**，不是贴图标。因为图标本身**长在任务栏里**，而任务栏在工作区**外面** —— 若锚定图标，面板会往任务栏里压进一个图标的高度。

## 二、弹窗开完就自己关：焦点是「抢」来的，不是「给」的

### 症状（实测）

```
visible=True  →  700ms 后  False
```

静置不动也会消失。

### 根因

「点别处就关掉」是靠 `Focused(false)` 事件实现的 —— 而这个机制**只在面板真的持有过焦点时才说得通**。

Windows 有**前台锁（foreground lock）**：一个不是由用户手势引起的窗口显示请求，可以被系统拒绝授予焦点。`DEEPSEEKBUDGET_OPEN_POPOVER` 那条启动路径就属于这种情况。于是窗口从未真正持有过焦点，随后任何一个 `Focused(false)` 关掉的就是一个**没人看见过的面板**。

### 修法

```rust
static HELD_FOCUS: AtomicBool = AtomicBool::new(false);

pub fn note_focus_lost() -> bool {
    // 用 swap 而不是 load，这样第二次 Focused(false) 不会重复关闭。
    if !HELD_FOCUS.swap(false, Ordering::Relaxed) { return false; }
    ...
}
```

**「没持有过焦点，就不算失去焦点。」** 在 macOS 上面板打开即获得焦点，所以这个门是透明的、不改变任何行为。

### 同源的第二个 bug：点图标关不掉

Windows 上点托盘图标时，**焦点先丢、托盘事件后到** —— 这个顺序 macOS 永远不会产生。于是焦点丢失先把手隐藏了，紧接着那个造成丢失的点击看到一个隐藏的面板，又把它打开。净效果：**能打开它的那个图标，关不掉它**。

修法是一个 250ms 的宽限窗口：焦点丢失后 [`REOPEN_GRACE`](../src-tauri/src/popover.rs) 内到达的点击**就是那次关闭**，不是重开请求。

> 教训：**「点击外部关闭」这类交互在两个平台上不是同一个事件序列。** 单个事件本身都没错，错的是顺序。

## 三、圆角：谁画这个角，只能有一个人

### 症状

窗口每个角都像「**圆角套圆角**」—— 一道曲线横切过另一道曲线，中间那道缝里露出亚克力。

### 根因

三个平台 API 的签名不一样，而差异正好在半径上：

| 平台 | API | 收半径吗 |
|---|---|---|
| macOS 26+ | `apply_liquid_glass` | ✅ 收，给 `CARD_RADIUS` |
| macOS < 26 | `apply_vibrancy` | ✅ 收，给 `CARD_RADIUS` |
| **Windows** | `apply_acrylic` | ❌ **不收** |

所以 Windows 上原生材质是一块**矩形**。而 **DWM 会给每个顶层窗口加它自己的圆角**。同时 CSS 卡片也在画 `--card-radius` —— 于是同一个角上有两条曲线。

### 修法

`styles.css` 在 Windows 上把卡片的半径**归零**，让窗口上只剩 DWM 那一条曲线：

```css
:root[data-platform="windows"] {
  --card-radius: 0;
}
```

代价：Windows 的角比 macOS **略方一点**。换来的是这个 app 唯一的窗口不再每个角都画两条互相打架的曲线 —— 这笔交换是划算的。

### 怎么发现的：不要用眼睛看角，用数字量

从窗口顶部往下**逐行扫描**，报告每行第一个与背景色差异超过阈值的列 —— 那一列**就是**边缘。于是打印出来的数列就是角的轮廓：

- **一条**曲线 → 平滑、严格递减、约一个半径后归零的内缩数列
- **两条**嵌套曲线 → 数列里有**断点**：第一段弧提前停住、一个台阶、第二段弧。**台阶的大小就是两个半径之差**

> 10 倍放大盯着一个角看，是描述出一个并不存在的形状的最快方式。**量出来的是几何，看出来的是印象。**

## 四、tooltip 会退化

macOS 的 tooltip 支持真正多行；**Windows 托盘 tooltip 硬上限 127 个 UTF-16 字符**，且多行支持没有官方文档保证。

所以 Windows 用**压缩版（3 行）**，完整信息交给弹窗。压缩形态由 `view.rs` 生成（`tooltip_windows_form_is_compressed`），长度由 `the_windows_tooltip_fits_the_platform_limit` 钉住 —— 文案的唯一来源仍然是 `view.rs`，这个约束在 Windows 上没有被绕开。

## 五、可验证性：不需要任何权限

> 这一节的标题原先是「Windows 反而更容易」。**那个比较已经作废**（见开头与 [macos.md](macos.md) 第五节）；下面这些方法本身仍然成立。

Windows 上做这件事只需要系统自带的 API，**不需要任何屏幕录制权限**：

| 手段 | 怎么做 | 用在哪 |
|---|---|---|
| 截屏 | `System.Drawing` 的 `CopyFromScreen` | 一切 |
| 点击 | `SendInput` | 驱动真实的托盘点击 |
| 按颜色找图标 | 在截图里搜像素 | **仅在已知要找什么颜色时可靠** |
| **两次截图求差** | 同一区域拍两张，相减 | **比色彩搜索强得多**：不用猜颜色，只问「哪里变了」 |
| **逐行扫角的轮廓** | 每行报第一个与背景差异超阈值的列 | 区分一条曲线还是两条 |

后两条是这里最重要的两个方法：**把「看着像什么」换成一个可以读的数列或一张差异图。**

### 怎么验证「点托盘 → 弹窗」这条链路

**不要从截图里猜坐标。** 这条链路卡了很久，**卡在方法上不是卡在技术上** —— 三次失败都源于同一件事：猜坐标。颜色搜索在同一个 24×32 区域两次给出互相矛盾的结果；放大截图目测看出了「一只蓝色鲸鱼」，是过度解读。

正确做法是**问 app 自己**：

```bash
DEEPSEEKBUDGET_REPORT_TRAY_RECT=1 ./target/release/deepseek-budget.exe
# stderr: DeepSeek Budget: tray rect x=1788 y=1032 w=32 h=48 centre=(1804,1056)
# 然后按这个坐标发一次 SendInput 点击 —— 弹窗正常打开
```

**自相矛盾的证据不是证据。** 一个方法两次给出不同答案，说明方法是废的，不是说明数据难拿。

### 两个坑

1. **屏幕几何会变。** 开发中途显示器从双屏 4480×1440 变成单屏 2130×1080，所有硬编码坐标**全部作废**。当时的截图脚本还把越界裁剪报成 `OutOfMemoryException`，把人往内存问题上引 —— **已修**，现在直接说「裁剪超出当前虚拟桌面，布局可能变了」。
2. **`CopyFromScreen` 的坐标空间是虚拟桌面，不是某一个屏幕。** 多屏时按主屏尺寸裁，会得到一张**看起来正常、实际错位**的图。

## 六、分发：免安装 exe

```bash
cargo build --release -p deepseek-budget   # → target/release/deepseek-budget.exe，实测 6.2 MiB
```

**不做安装器。** `tauri.windows.conf.json` 里 `bundle.targets: []`，并且**实测确认**完整的 `npx tauri build` 不产出 `bundle/` 目录 —— 这条是量出来的，不是读配置推断的。

### 还没证明的那一跳

**没在干净机器上试过 WebView2 依赖。** 开发机的 Windows 11 已经装了 WebView2（Edge 带来的），所以在这里**无法验证**「一台没装过的机器上能不能跑」。

这条不许写成已完成。

## 七、开机启动：一个只能读不能写的键，和一对不能省的引号

### 一条记着绝对路径的登录项，遇上一个会被移动的绿色包

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 下的值形如 `"E:\...\deepseek-budget.exe"`，任务管理器 → 启动 里能看到它。**但它记的是绝对路径**，而绿色 exe 的定义就是「放在哪都行」—— 一移动，这条记录就失效了，而且失效得**很安静**：任务管理器里那条还在，只是下次登录什么都不会发生。

所以 `autostart.rs` 每次启动都跑一次 `reconcile`：**登录项存在 ⇒ 把它重写成现在这个自己**。实测（本机）：把 exe 复制到 `…\Temp\DeepSeek Budget portable\`，运行那个副本，注册表里的值自己变成了新路径 —— 而且带引号。

### 引号不是风格问题，是能不能跑的问题

同一份路径，写进 `.cmd` 直接执行，加不加引号的区别：

```
> C:\Users\me\AppData\Local\Temp\DeepSeek Budget portable\deepseek-budget.exe
'C:\Users\me\AppData\Local\Temp\DeepSeek' 不是内部或外部命令
```

而且**没有任何进程起来**（`tasklist` 里查不到）。加了引号则正常启动、托盘图标出现。

官方插件 `tauri-plugin-autostart` 走的是 `auto-launch 0.5.0`，那里写的是 `format!("{} {}", &self.app_path, &self.args.join(" "))` —— **不加引号**。不带参数时它靠 CreateProcess 的「整串兜底」还能跑；一旦带上参数，最后那个候选就是「路径 + 粘上来的参数」，必然失败。我们这条路是**无条件加引号**：一种形态比两种好推理，`reconcile` 的整串比较也因此只需要关心路径变没变。

> 怎么验证「那条命令行真的能跑」而不重启：把注册表里那条值原样取出来跑一遍，然后问 app 自己在哪 —— `DEEPSEEKBUDGET_REPORT_TRAY_RECT=1` 报 `centre=(2234,1416)`，按颜色找图标报 `centre=(2233,1415)`。**两个独立方法对上了**，而停掉 app 之后同一区域 `NOT FOUND`。这证明的是「写进去的东西是可执行的」，**不等于**「Windows 在登录时会执行它」—— 后者只有一次真实登录能回答。

### `StartupApproved\Run`：只读，不写

这个键用**值名**索引，所以**删掉 `Run` 下的值并不会清掉它**。含义很实际：用户一旦在任务管理器里把这个条目录关掉，我们之后**再写一条同名的也不会启动** —— 开关会显示「开」，而实际永远不启动。这就是「一个跨重启都在撒谎的开关」。

那条键里本来就同时有这两种形态，正好都摆出来：

```
<应用 A>                 REG_BINARY    020000000000000000000000   ← 启用
<应用 B>                 REG_BINARY    020000000000000000000000   ← 启用
<应用 C>                 REG_BINARY    030000000000000000000000   ← 禁用，时间戳是零
<应用 D>                 REG_BINARY    03000000C13E9AF7C80BDD01   ← 禁用，带时间戳
```

**判据是第一个字节**（`02` 开 / `03` 关），后面 8 字节是个 FILETIME，**不是**第二个信号。

> 这一条是被「已关闭、且时间戳全零」那一行纠正过来的。最初照抄的是 `auto-launch 0.5.0` 的规则 —— 它只看「末尾 8 字节是不是全零」，于是在 `03 00 00 00` + 全零时间戳这一格上**读反**：明明被关掉，却报「开」。那个字节数组后来被钉成了单元测试（`the_approval_blob_is_read_from_its_state_word_not_its_timestamp`），四个实例都取自真实的注册表键。
>
> 教训和第三节「不要用眼睛看角，用数字量」是同一条：**一个看起来有来源的判定，要问它的来源是不是覆盖了真实数据里的每一种形态。** `auto-launch` 写「启用」记录时确实写 `02` + 八个零，所以它对**自己写的那种**是对的 —— 只是对别人写的不是。

我们的做法：

- **只读**（键不存在、值不存在、或形态不认识，一律视为「没被挡住」——只报告 Windows 真的记下来的东西）。自己去写它，等于覆盖用户在系统里的选择。
- 因此界面会出现第三种状态：**「关」+「被 Windows 挡住了」**，并指向任务管理器 —— 因为那个开关不在我们的面板里，说了才能去修。

## 八、跨平台发布 = 两次原生构建

**从 macOS 交叉编译到 Windows 不可行。** Tauri 官方没有交叉编译路径：`rustup target add x86_64-pc-windows-msvc` 只给你 `rust-std`，没有 `link.exe`、没有 Windows SDK、没有 WebView2Loader，而 NSIS/WiX 打包工具本身就是 Windows 可执行文件。

推荐路径是 `windows-latest` 的 GitHub Actions + `tauri-apps/tauri-action`。**不是一次交叉编译，是两次原生构建。**
